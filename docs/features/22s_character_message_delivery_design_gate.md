# C4 多气泡与间隔送达：设计入口与停止门

2026-10-06。状态：需求与代码基准已核对，工程契约尚未冻结，未实现。
承接22m、22n、已完成22r；用户允许按阶段推进至设计或打包边界。本记录不把候选方案当作用户确认，也不将文档提交称为功能完成。

## 1. 玩家目标与已确认范围

角色聊天要接近微信/QQ：一次回应可以只有一个气泡，也可以有多个自然短消息，程序间隔显示。不是机械按标点拆句，更不是每个气泡调用一次模型。2026-10-06用户新增明确要求：显示间隔不完全关闭，最短0.1秒；不强制所有角色采用短句网聊腔。玩家能在后续消息尚未送达时插话，不被整个表演队列阻塞。插话不再一律取消剩余消息，见第7节，替代本记录此前的统一取消建议。

主线是角色聊天，不是故事模式、插件平台或主动联系调度。C5主动联系依赖这里的送达底座，但不得顺手实施。权限仍按当前会话隔离，OOC保持当前回合说明，不能变为角色经历。

## 2. 真实源码基准与必要性

本地提交a5d202e；版本1.6.0-dev.19。C3历史验收Python630、Node116、Edge39；本轮仅核对源码与文档，没有重跑或新增运行验收。

- `core/character_chat/contract.py`：输出`reply`是单字符串，最多8000字符；`plan_turn`创建一条`ai_message`，一次提交全部账本操作和整轮inverse。
- `core/character_chat/models.py`：正式回合校验`user_message`/`ai_message`及整轮inverse，不能直接增加数组而保持旧校验不变。
- `core/character_chat/service.py`：最新预览及AI消息ID基于单条消息；撤回倒转整轮账本。当前`delivery=stream/non_stream`是传输方式，不是多消息送达状态。

因此前端拆分不能兑现“未送达内容不是经历”；也不能将完整候选回复先写入上下文，再只隐藏其后半部分。流式token是预览，不等于正式消息。

## 3. 冻结前必须闭合的约束

| 领域 | 必须明确的契约 | 不可采用的捷径 |
| --- | --- | --- |
| 身份/协议 | 新输出协议、存储版本、组ID、稳定气泡ID与顺序；旧v1/v2读取与旧pending恢复 | 给旧v2偷偷增加messages字段或猜分句迁移 |
| 生命周期 | 生成候选、待送达、已送达、取消/中断；第一条何时正式提交 | 把浏览器已显示等同服务端送达 |
| 插话 | 新玩家行动和送达竞争在同会话锁/CAS下排序；已送达保留，余下不再进入新请求 | 客户端先隐藏再异步取消，迟到timer复活旧队列 |
| 账本/高光 | 每个op依赖的气泡来源、提交时刻、supersede前置依赖、inverse与容量预留 | 仅检查引用ID后逐条执行，忽略操作之间的依赖 |
| 恢复 | 保存失败、丢响应、崩溃、重启、页面重载分别处理；服务端权威与幂等 | 页面每次打开重播或自行补送积压 |
| 撤回/重生成 | 整组作为操作单位，只逆转实际送达及已应用op；后续玩家已回应的组不可任意替换 | 把未送达草稿归档成正式经历 |
| 输入/输出预算 | 气泡数、总字符、间隔范围及关闭方式；原文召回按整条来源处理 | 增大硬容量或把每个气泡当额外免费回合 |
| UI/并发 | 会话设置入口、送达中提示、插话、取消、未读、后台切换；流式预览不重复最终气泡 | 前端定时器拥有唯一权威或依赖当前显示会话 |

此前1–6气泡/整组8000字符是候选参数，尚非冻结值。用户已确认的大方向不重复询问；可逆工程参数由契约设计论证。只有改变核心玩法/数据生命周期的取舍才需要用户选择。

## 4. 关键场景：A/B/C中途插话

模型一次生成A、B、C以及来源账本提议。A正式送达后，玩家在B之前发送X：

1. 以服务端同会话事务顺序确定B与X谁先发生，不能用浏览器看到的顺序裁决。
2. 旧建议是X接受后一律取消未送达部分；用户在本轮细分后，此规则不再成立。必须区分连续表达、等待对方回应以及先回应再接回话题，见第7节；已送达部分始终保留，不把尚未发生的内容当经历。
3. 只把实际送达内容放入下一次上下文、世界书匹配、来源索引与记忆取材。
4. 依赖取消消息的账本操作不可应用；已应用操作的逆操作必须准确。跨操作依赖不能被部分应用破坏。
5. 失败不能任意复活已取消队列，保存失败不能让UI宣布已送达。用户要求后台及重开仍可收到已生成内容，替代此前“重启不补发”的统一建议；准确的离线恢复时间和取消规则尚待设计，不能声称程序彻底退出时仍在执行。

这是C4的核心验收，不是更漂亮的气泡动画。

## 6. 验收清单与停止边界

假模型一次调用产生多气泡；1条/最大条数/超长/坏协议；流式不产生提前经历；最短0.1秒显示间隔；A/B/C插话顺序及三种表达策略；重复送达事件；切换会话；丢响应/保存失败/崩溃；重新加载不重复送达但能核对恢复已生成队列；撤回和重生成准确逆转；OOC不入经历；未送达不入记忆/世界书/召回；旧v1/v2/pending无猜测迁移；未知新版本拒写。

## 7. 用户细分与角色扮演核心（2026-10-06追加，现行方向）

### 明确确认的产品要求

- 一组连贯内容一次LLM请求生成多个气泡，拆分服务于自然打字/阅读习惯；不是每气泡重新推理。
- 连续表达：持续“对方正在输入中”，短间隔发送多个气泡，然后回应玩家插话。
- 等待回应：角色可以只说“今天遇到一件事”，期待玩家询问后再细说；必须是真正等新输入，不能把后续讲述藏在固定时间队列里。
- 回应后接回话题：先回应玩家的新内容，再自然说“你猜我遇到什么事”；不是无视玩家或重复旧句。
- 气泡动画至少0.1秒间隔；撤回/重新生成按整批处理。
- 退出界面/重开后仍可收到消息，聊天列表头像显示未读，点开能看最新内容。实现必须如实区分窗口后台与程序退出。
- 核心是符合人设、现实交流感与更体贴可靠的伴侣体验；不是逼真复刻冷落、操纵或失忆，也不是全角色无条件迎合。尊重明确边界和玩家行动权。

### 待设计的机制，不冒称已实施

- 表达策略由同次模型请求依据人设和语境选：连贯短批、说到互动点等待、回应后接回话题。它们不是让玩家每回合点选的三种UI模式。
- 连贯短批内插话先接收并保存，下一回复合并处理插话；批次末尾才开始新的请求，避免一气泡一调用。停止、场外纠正、明确更正或撤回不能被当作普通插话排队忽略。具体抢占与多条玩家输入的合并规则须进一步冻结。
- 等待回应时后续细说尚未成为自动发送任务；角色可以保留简短“想分享的事情”作为自身意图，但不能登记玩家已听过或答应过。
- 接回话题只允许未过时且有来历的内容；玩家换话题、表示不感兴趣或出现更重要事项时，不强行拉回。新回应依赖新输入，需要新的正常回复调用，不把旧预写句子冒充已理解新消息。
- 后台运行可用本地服务继续送达并持久记录未读。进程彻底退出/关机不运行计时或调用；可在下次启动核对已保存的候选队列，按明确恢复规则补齐，但不能伪造离线期间已实际执行/已读。若要真正离线生成需常驻服务或云端，后置独立范围。

### “AI如何扮演好角色”的现状与本阶段补齐项

已设计：22c自由人设/可选精神内核、稳定人格与短期状态分开、冻结人格与来源记忆；22m角色动机/知情范围/行为小步/玩家边界；表达示例、世界书及授权偏好参考。源码prompts.py已落实人设/示例来源隔离、偏好不覆盖人格及C3单步自主指导。长期人格演变未开放，也未证明真实模型已经自然。

本阶段P1补齐：在一次回复中将“当前知道什么→自己想做什么→对玩家刚说的话如何理解→表达/等待/接话策略→气泡”结合起来。只输出必要的结果和短状态，不要求暴露逐步思维链；不新增心理分析请求。体贴指准确回应、记住重要约定、尊重边界与情绪节奏，不是永远答应或故意唱反调。人设中的独立立场、用词与表达示例应造成可观察差异。

验收分开：程序严格验证策略/消息/等待/来源/未读；真实模型对同一场景的角色差异、接话自然度、过度反问/迎合、记忆运用需要单列质量评价。假API通过不能证明活人感。
