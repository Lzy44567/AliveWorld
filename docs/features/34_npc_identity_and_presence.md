# NPC身份与当前场景显示：B阶段最小设计

日期：2026-10-13。类型：核心功能修复/体验优化，P1。玩家目标已确认，以下工程方案已整理，尚未编码；A的正文后果语义复核仍未完成，不偷偷切换主线。

## 玩家获得什么

“门口的守卫”报出姓名之后，侧栏同一张卡改名，不增加另一张。离开现场后卡片退出侧栏，身份和原有经历不因此删除；再次相遇时沿用同一个人物。玩家不必填写ID或手工整理重复卡。

## 现有实现与本片边界

- `NpcPresenceTracker`已有明确离场词和连续三回合未提及的旧清理机制；不重复实现。现有名称子串提及不能可靠判断“想起某人”与“此人在场”，改名也没有稳定引用。
- `StateManager`已有隔离计算、metadata保存，GameSession已有存取/撤回/重生成事务。身份归入本局state_meta，与回合一起提交或回退，不建第二数据库。
- `EntityRepository`仍按实体名称写YAML；本片不自动把每个路人升为暗流实体，也不批量改实体文件名。实体ID与NPC身份合流放C阶段，不能宣称本片解决了幕后所有实体身份。
- 不做跨存档认人、自动相似名字合并、公开真名推断、完整人物记忆或新管理页面。

## 模型与程序分工

正文请求可附可选`npc_identity_updates`列表，每项包含显示名称`name`、已知身份`id`或明确旧称`previous_name`、可选`present`布尔值及说明依据`reason`。普通状态继续沿用`npc_states`，旧模型不必立即改格式。

- Python首次记录人物时分配本局稳定ID，保存当前显示名、已确认别名和最后状态；模型只能引用已提供的ID，不能凭空指定另一个人的ID。
- AI依据本回合场景明确指出“这是原来的某人”“离场/重返”，程序验证引用和作用范围；同名不等于同人，相似字符串不触发合并。
- 改名必须指向已存在身份，并且新显示名未被另一身份占用。歧义时本回合不合并、不覆盖另一人，保留输入并给出可读错误；可在后续称呼中附加区分说明。
- 显式`present=false`优先于正文提及；回忆名字不能让卡复活。再次在场需明确`present=true`或符合旧兼容路径的首次实际出现。未提供新协议的旧回合保留旧生命周期行为，不假称语义识别已完美。
- 身份变更与`npc_states`的新旧名称需统一到同一对象；同回合两份互相冲突状态不得静默择一。

## 请求与资料边界

同一次正文请求完成，不新增“认人AI”调用。只附当前侧栏人物及本次输入明确提及的局内已知身份/别名摘要；不每回合发送整个历史名册。身份记录只来自玩家已看到的角色称呼，不从暗流秘密档案泄漏真名或身份。

长期经历仍保留在正文、已有角色/实体档案中；身份小档案只保存关联、别名及最后状态，不复制完整聊天。离场后不调用AI补齐路人生活。

## 生命周期、兼容与恢复

- 归属当前故事，随存档复制/删除；无全局共享。回溯恢复到该回合的姓名、别名、可见状态及身份索引。
- 旧档在首次成功状态更新时登记已有侧栏人物；只读载入不写回、不扫描其他存档、不猜测并合历史同名人物。
- 侧栏删除代表隐藏/离场，不抹去身份历史，不删除角色卡或世界账本。档案彻底删除需未来明确入口，本片不增加隐式级联删除。
- 先在StateManager副本应用，生成或持久化失败不得留下半个改名。两个故事使用各自metadata，不共享对象。

## 验收出口

1. 无名守卫→阿林：仅一张侧栏卡、ID不变、保留旧称；新旧名冲突不覆盖另一人。
2. 明确离场→后续只是提及→真正重返：中间不显示，再现仍同ID。
3. 保存重开、撤回改名、重新生成另一姓名、失败重试均恢复正确，无多余实体文件。
4. 假模型真实应用请求＋浏览器显示确认新旧名与卡片数量；旧NPC清理测试继续通过。
5. 不读取玩家存档，不创建新付费后台服务。完成后再进入C，不顺带新增死亡保护默认值或完整记忆系统。

无需用户再回答ID字段等实现细节。C阶段“重要角色定义/死亡默认”仍是独立产品选择，不阻塞本片。
