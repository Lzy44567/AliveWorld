# C4 角色接话与三种输出体验：更新设计

2026-10-06，Astra更新。承接22c/22m/22n/22s。本轮仅设计；C4-0已提交7f5265e，仍是single reply短接话指导。Python637/Node116/相关Edge2项是此前证据，本轮未运行验证。668e706和本文旧版新增停止入口的建议已被最新用户意见否定；本稿完整替代旧设计，不保留矛盾的现行要求。

## 1. 已确认方向及范围

主线是角色聊天：符合人设、有来源连续性、体贴可靠且保留立场。不是建立心理模拟器或通用调度平台。

- 用户区分供应商流式、本地逐字显示、多气泡按字数间隔，要求允许开关；一次正常请求生成一批，本地动画免费，不每气泡调用。
- 不建议新增停止按钮：来不及反应且截断处理复杂。本稿不以停止入口为设计前提，也不擅自删除角色已有停止生成功能。
- 保留连续短批后回应期间的新消息、只开话题真正等待追问、先回应新话再接回旧话题三种角色表达目标。
- 后台/重开能收到已生成内容、显示未读；撤回/重生成按批，未发内容不能记作双方经历。
- 每字0.1秒是示例，历史最短动画意见不等于冻结所有默认值。模型不输出任意秒数，不新增玩家速度滑块。

旧版“三模式统一新增停止入口”不再是当前确认需求；故事/工坊停止不纳入本轮。本文推荐与已确认分开；第7节说明已确认连续短批的实时理解限制，不重复要求用户改选另一套队列方案。

## 2. 角色如何扮演及现状

C4-0已在M3/C3 core加入理解新话→依据冻结人设/正式事实/已有intent选择小动机→完整回应或真正等待→适当接回旧话题的短指导。仍是v1/v2 single reply，未实现多气泡/插话队列/后台送达。

角色不凭空制造重大事件来活跃，不代写玩家行动或同意，不机械迎合或故意反对，不每轮空泛反问。体贴体现为具体回应、记住约定、尊重拒绝；人物差异来自理由、立场和表达，不统一短句腔。瞬时计划不强制入账，不增加心理分析请求或思维链输出。

真等待只生成当前要说的部分，然后结束本组：不存在定时自动讲完的后半段。新输入后才正常调用。接回旧话题同样在理解新输入的新回复中完成，不把旧预写文本冒充理解了新消息。

## 3. 三种机制简明表与组合建议

| 机制 | 输入与展示 | 正式性与费用 |
| --- | --- | --- |
| 供应商流式预览 | 同一次请求逐步返回，显示临时文本 | 完整校验保存前不是正式历史；不是第二次调用 |
| 本地逐字动画 | 对已验证保存的文本逐字揭示 | 纯本地免费动画，不改变消息/账本，不每字持久化 |
| 多气泡间隔发送 | 同次请求完整产出数组，Python按文字量安排后续气泡 | 到期提交才正式送达，不每条调用模型 |

“本地免费”不表示生成内容免费。供应商速度不等于固定打字速度；开三个效果不是调用三次。

**工程推荐：传输与显示分层，一个时刻只有一套显示时间轴。** 流式开关选择请求传输；本地逐字和气泡间隔选择表现。逐字或间隔打开时，先接收完整结果并验证，之前只显示正在输入，不展示同段实时预览；即使流式传输开启也只是流式接收。设置必须解释这项组合，不能静默让一个开关失效。

两者都关闭时可显示流式临时预览，成功后原位转正式，不再次逐字播放；流式也关闭则完整验证后直接显示。多气泡结构不因间隔关闭而消失，只取消模拟等待。另一可选UI是互斥显示选项，见第10节。

逐字与间隔同时打开时，动画与间隔共用时间轴：下一气泡计划时点覆盖上一气泡揭示时长和短间隔，不先按字等一遍再逐字等一遍。动画落后于已到期下一条时，直接补全前条再显示下一条；不能反过来阻塞服务端。具体计数和上限由工程样例校准，尚未冻结。

## 4. 计时、预览、正式送达与已读

首条不再叠加整次模型生成等待；后续在仅间隔模式可按下一条字数计算，在逐字组合模式抵扣已占用动画时长。用Unicode可见文字量近似而非UTF-8字节数，校准长句/短句/标点/emoji并设置上限，避免长文数十秒空等。

正式送达由服务端决定，不由页面timer决定。已正式送达但动画尚未显示完的整条消息已经到达会话，可作正式来源；逐字仅是展示。尚未正式送达的后续气泡不可进入上下文、世界书匹配、召回、经历或未读。“已读”再由客户端确认，不能等同已生成或已送达。

当前stream_json.ReplyPreview只逐步抽取根reply字符串，是未验证预览，不能直接处理新数组成为正式气泡。首版多气泡模式建议完整缓冲后校验，不扩建半JSON数组提交器。协议错误/缺字段/失败残片从不入账；成功按稳定ID替换预览，不重复追加或重播同段动画。

真正等待是本组结束、没有自动后续任务；和上述所有时间独立，无输入不自动再调用。

## 5. 最小协议与存储候选，未冻结

现有protocol.py只接受v1/v2；contract.parse_result/plan_turn仍单reply整轮事务；models.validate_records仍双消息回合；service.session_summary取单条AI预览。不能偷偷给v2加数组或把前端拆分称为领域送达。

候选新协议仅messages:[{local_id,text}]、ledger_ops、memory_annotations。无需delay、情绪分数、通用策略/心理状态字段；本组在互动点结束即可表达真等待，不必另建持久wait状态。程序分配group_id和稳定message_id，local_id仅用于本次候选来源映射。

预算候选1–6气泡、整组8000字符、最多6项op/注解，须合成校准；不扩大既有总容量。组最少保存attempt身份、输入ID集合、上下文截止点、候选、已送达前缀、账本计划、实际inverse和终止原因，不每字保存。

生成中→候选验证保存→送达中→完成。候选为会话私有草稿，不是正式历史；删除会话一并清理，不跨会话共享，诊断不默认导出正文。未说出的预写部分不能算已告知玩家。

## 6. 尽量减少部分事务

间隔关闭可整组一次原子提交、整批inverse；只有正式间隔送达需要逐条事务。本地逐字动画本身不引入部分提交。全部候选先严格验证和检查容量，不能A发出才发现C协议非法。

**推荐账本简化：整组完成时一次应用全部op/注解。** 送达中正式原文存在但暂不应用本组推断；下一正常请求在组结算后启动，因此能看到一致的账本。不为每气泡建独立op提交图。

正常连续批发完后结算；异常导致只有正式前缀时，仅保留所有来源均正式、权限仍有效的op，依赖未发气泡者不应用，不能改写证据凑记录。实际op/inverse/组结算同事务，失败先恢复，不开下一请求。首版禁止同组重复supersede同一目标、引用同组新entry或链式操作；不建立通用依赖图。

容量先预留，送达中手工修改账本串行或显式冲突；不能因途中容量不足悄悄丢记忆。撤回只逆转实际应用op。为简化而把完整候选写进正式ai_message再隐藏，不可接受。

## 7. 玩家连发，不依赖停止按钮

输入随时保存，保留各条ID、顺序和OOC，加入有界待回应集合；不拼成伪造单来源。每会话最多一个正常生成请求，批次边界原子认领当前输入集合，一集合一次请求；后到输入留到下一边界。不每条取消重开，不增加分类模型，不用关键词猜抢占。

**首版沿用已确认行为：连续短批发完，再统一回应期间新增输入。** A/B/C已生成、A后收到X/Y，则继续B/C，批结算后一次正常请求认领X/Y。首条前或生成期间收到新输入也保留到下一批，不自动取消已付费请求、不丢弃余量、不新增停止入口。

必须披露限制：A之后玩家说“不是这样，别继续那个动作”，旧B/C尚不能理解这条未来输入，可能在下一回复纠正前继续出现。短且有界的批次能缩短窗口，但不能消除它；不得宣称实时边界处理已实现。下一正常回复必须回应新边界、纠正过时前提，不以旧批文字证明玩家接受，不继续依旧语境推进。程序不添加关键词取消或独立分类调用来假装解决语义时效。

自动丢弃余量仅留P2候选，非首版主线、非当前推荐、非待用户重复回答的门；它会改变已确认体验并增加截断生命周期，只有未来明确要求才重新设计。

服务端事务决定输入和气泡的正式顺序，普通输入追加不使旧批失效。client_action_id及group_id+序号用于幂等。现有base_revision检查不能直接删除；应区分追加输入/已读更新和撤回改语境，用组有效性与历史截止点校验迟到结果，精确CAS/epoch字段留工程门。

## 8. 恢复、未读与批操作

| 情况 | 推荐行为 |
| --- | --- |
| 后台/切会话，服务仍运行 | 继续有效候选送达，累计未读，不播放不可见逐字动画 |
| 重开已送达历史 | 直接还原，不重演打字和历史间隔 |
| 进程退出/休眠 | 期间不执行不调用；恢复核对有效候选及输入，用真实恢复时间继续，不伪造离线执行 |
| 请求中崩溃 | 标interrupted、保留输入，显式重试，不自动重复付费 |
| 候选保存后丢响应 | 读回原组、不重生成；同气泡幂等 |
| 保存失败 | 不广播成功、不增未读，不留下半套inverse |
| 批撤回/重生成 | 推荐批结算后且无后续输入依赖才可操作，不另加发送中截断路径 |
| 重生成失败 | 原正式批保留；成功原子替换，旧分支归档且不再作来源 |

角色已有停止生成保持现有语义，不扩大/删除；若新格式与旧API有兼容冲突，工程门必须先说明，不能偷偷变成停止余量。正式归档与候选分区，失效候选不能因重启复活。

未读推荐单调last_read_ai_seq：前台确实展示后确认，不能超过已送达序号；后台不自动已读，旧ack不覆盖新消息。逐字未显示完可延后该条ack，但不改变正式送达事实。列表预览只取正式消息。

## 10. 一个待讨论的显示体验

**开启本地逐字或气泡间隔时，是否接受先等完整结果，再按动画显示，不同时显示供应商实时预览？** 推荐接受；流式可用于接收，显示只用一套时间轴。也可做“实时预览/逐字/气泡”互斥显示选项以减少组合解释；都不增加请求。这只是显示组合的产品选择，不要求改选另一套输入队列。

计数、字耗时和上限由工程样例校准，不再询问模糊“谁控制快慢”。未回答时保留显示推荐待讨论；连续短批后统一回应新增输入已经明确，不再反复提问。真实会话迁移仍需工程验证，不由显示选择自动授权。

## 11. 验收不变量与出口

- 一集合一次正常请求，本地动画零额外调用，气泡不逐条调用。
- 半JSON/失败预览不入正式来源；成功不重复、不再逐字重播同段。
- 逐字+间隔不双重等待，后台无动画仍权威送达，重开不重播。
- 真等待没有自动后半段，无新输入不自动调用。
- 普通新输入保存并在连续短批后统一回应，不自动截断、不用关键词/LLM分类取消；即时理解未来输入不是当前能力。
- 候选/正式送达/已读分离；记忆仅依正式来源，失败重试不复活草稿。
- 不新增必用停止按钮、不删除角色已有停止，不把三模式停止当当前确认需求。

本轮是设计更新，不是产品/工程全部冻结。下一编码片可为组合确认后的single reply本地动画；完整多气泡可沿已确认连续批语义继续闭合工程契约，不被自动截断这一P2替代方案阻塞，不能宣称角色聊天已基本完成。
