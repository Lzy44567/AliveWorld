# C4 角色接话、消息组与真实等待：分阶段设计

2026-10-06。Astra设计稿。承接22c、22m、22n、22s；基准由主代理核对为63e98bd/C3。本文只设计，不证明实现。Python630/Node116/Edge39是C3历史证据，不是本轮结果。用户允许完善设计并继续独立代码片，但气泡间隔控制权尚未决定；不把这项授权解释为全部候选机制已确认。

## 1. 当前主线与可以立即冻结的小片

主线仍是角色聊天基本完成，当前阶段是C4：让角色有理由地接话，并支持一次生成、分批送达、真实等待和插话。最终目标不是一个会延迟的聊天框，而是符合人设、记住有来源的重要信息、尊重玩家行动权且体贴可靠的对话伙伴。

**C4-0可独立冻结并实施：现有M3/C3 core中的简短接话指导。** 保持现有single `reply`，不改输出字段、存储版本、计时、UI或插话API。指导覆盖：先回应玩家刚说的新内容；结合冻结人设、已知事实和已有intent选择当下的小动机；表达一个完整小步或在真正需要玩家回应处结束；合适时自然接回有来源且未过时的话题。避免持续套问、凭空创造重大事件、无条件迎合及为显自主而反对。普通瞬时意图不强制入账，不输出思维链，不增加调用。

此片与“间隔由谁控制”无依赖：一次短回复后没有自动后续队列，本来就只能等新输入。它只能补齐行为指导缺口，不能兑现多气泡、送达中插话、后台补送或未读。测试验证提示词实际装配、预算、override与来源/OOC边界，不能用字符串断言证明自然度。legacy协议不顺带迁移；保持当前M3/C3装配范围。

实施记录：主代理全文读取后落实C4-0；`prompts.CONVERSATION_GUIDANCE`由既有四个M3/C3 core引用，无新slice/输出字段或持久状态，旧legacy和显式core覆盖语义保留。新增7项`test_character_conversation_guidance.py`验证装配/预算/来源/哈希/旧协议与覆盖，不将它们称为语义质量测试。Python637、Node116、相关Edge2项通过，详见TESTING；本节之外仍未实现。

其余C4设计以下均是**待评审建议**，不是已冻结存储迁移或可直接全量编码的契约。用户不必逐个批准工程子阶段；只需回答第10节实质性产品选择，再由工程完成一致性门。

## 2. 已确认、建议、未决分开

已确认的P1核心需求：

- 一次模型请求完整生成一组自然消息；一组可单条，也可多条，不按标点机械切割，不按气泡重复调用。
- 连贯短批可保持正在输入，间隔发送；玩家插话先接收，角色完成短批后回应。
- 角色可以只抛出话题并真正等玩家询问；不能把“等回答”伪装成固定延时后自动讲完。
- 新回复先回应新话，再按合适程度接回旧话题；不拿预写文本冒充已理解插话。
- 撤回/重生成按整批。后台或重开能收到已生成内容、看到未读；进程退出不虚构仍在运行。
- 人设上更体贴可靠，而非无限顺从；尊重拒绝、边界与玩家行动权。

此前0.1秒作为最短动画间隔已记录；最新用户明确具体间隔及控制权还需设计。本稿保留其历史约束，不据此冻结默认速度、上限、滑块或模型delay字段。

本稿建议：有界连续批+批末等待；服务端权威逐条送达；本地服务运行时继续送达，重启只恢复已保存候选、不自动重新付费生成；结构化停止具有确定性优先权。

未决：具体间隔权力分配，以及普通插话与需要立即中断的文本入口如何兼顾。见第10节；不以“用户没反对”当批准。

## 3. 玩家循环和角色如何扮演

最短路径：进入会话→正常发台词（可带本轮OOC）→看角色回复/正在输入→随时发下一条或停止→角色回应新的内容。气泡分段策略不要求玩家每轮选模式；控制仍留在聊天页面。未读在列表头像旁提示，点开定位最新内容但不强制把正在读的旧历史拖到底。

模型在同次正常回复中完成行为选择，不另调用“心理分析器”：

1. 理解新输入要回应的事实、问题、情绪表达或边界；不能为了讲自己的事跳过它。
2. 从人设、正式历史及有来源intent选择现在想表达/维护/邀请的一小步。人物可克制、热情、直率或谨慎，不统一变成客服腔或短句腔。
3. 判断这一小步能否完整说完，还是需要玩家作选择。前者产出完整短批；后者把本组停在互动点。
4. 若有旧话题，先判断是否仍相关。被拒绝、已结束、已纠正或被更紧要事项取代的内容不强行接回。不凭空捏造“今天发生的大事”增加活跃度。

体贴体现为具体回应、记住重要约定、不逼玩家反复解释、不故意冷落或以依恋施压；可靠不等于每次认同。需要澄清边界可以问，普通自有行动不必重复请示。真实质量另验“同场景不同人物的理由和行动有差异”，不能只统计短句数或反问率。

三个例子（说明机制，不做固定模板）：

- 连续批：A“找到了。”B“在你上次说的那家旧书店。”C“我先替你问问品相。”玩家在A后发X，X即时被保存，下一请求才理解X；B/C没有假称已读懂X。
- 真等待：只发送“那家店有件事想告诉你。”并结束组；玩家不回复便没有新任务。玩家问后再一次正常请求细说。只能分享有来历的信息，不把这个例句当编造许可。
- 接回：玩家先问“你吃饭了吗”，先具体回答，再自然说“说回刚才那本书……”。玩家说“不想聊书了”就不接回。

## 4. 三种时间不能混为一谈

| 概念 | 权威与作用 | 不代表什么 |
| --- | --- | --- |
| 视觉展示间隔 | 客户端动画与阅读体验；不得更改历史事实 | 不是正式送达，不决定何时允许玩家说话 |
| 正式送达节奏 | 服务端按已冻结策略提交气泡、来源与未读 | 不是浏览器timer，不等玩家屏幕确认 |
| 语义等待 | 本组已结束，等新玩家输入才能开始下一回复 | 不是长delay，不预写隐藏后半段自动续讲 |

为了不让展示与事实长期错位，建议前台随正式送达事件显示，只加有界短动画，不在前端藏整组。重开显示已送达历史可直接还原，不需要重演几分钟前的打字动画。后台已送达可以成为新上下文，未被玩家看见不等于没有送达；“已读”另有游标。

间隔方案权衡：

- LLM给具体秒数：富表现力，但不稳定、难预测，不能授予无限拖延或调度权限；必须代码限幅。
- 玩家固定速度：明确可控、易验证，角色差异主要来自措辞和分段，但节奏表现较少。
- **推荐混合**：模型只决定自然分段和哪里结束等待，程序产生有界节奏，玩家可调整阅读速度；首版不让模型生成任意秒数。这里的推荐未获批准，不编码设置、默认数值或delay schema。

不论选哪种，模型不能取消停止按钮、延长等待到自动收费、越过玩家选择点，程序退出也不执行计时。

## 5. 候选输出与最小领域结构（工程门未冻结）

当前实况：`protocol.py`只接受reply.v1/v2；`contract.parse_result`严格单reply；`plan_turn`一次生成user_message/ai_message和整轮inverse；`models.validate_records`验证双消息回合；`service.session_summary`取单条AI预览。现有stream/non_stream只是传输方式。不是给前端加数组即可完成。

建议新身份`character.reply.v3`，不偷偷扩展v2。候选结果包含`messages:[{local_id,text}]`、`end:"yield"|"await_user"`、`ledger_ops`、`memory_annotations`。`end`只描述批末语义，不是抢占权限；两种值都不会无输入再调用。`yield`是完整回应已结束，`await_user`强调到选择点停止。接回话题是新回复的内容策略，不建第四套调度状态。

首版候选预算沿用22s的1–6气泡、整组8000字符、最多6个op/6个注解；这些数字需合成预算测试后冻结，不扩现有总容量。程序分配group_id和稳定message_id，模型只能用本请求限定local_id引用候选气泡，验证后映射；不能让模型自造全局ID。取消或归档的草稿不进入allowed_messages。

组保存：生成attempt身份、输入消息ID集合、上下文截止序号、候选列表、送达前缀、待应用op计划、实际inverse及终止原因。正式消息有单调conversation_seq和真实committed_at；撤回单位是group，不是一个气泡。组外新玩家消息是独立正式输入事件，不能为兼容旧turn伪造空AI回复。

最小状态：生成中→候选已验证且保存→送达中→完成；生成失败/取消与送达停止分开。候选以连续前缀送达，不出现B已到而A未到。持久候选是私人草稿，不是正式历史、未读、世界书匹配、召回来源或关系经历。删除会话一并删除，不复制到全局；诊断默认不输出正文。

不增加持久“心理状态/话题规划器”。确需跨回合的意图复用已有合法intent及正式原文；未说出的预写内容不能当已告知玩家。UI显示“正在输入”意味着仍有生成/送达任务；真正等待、停止、失败后立即结束提示。

## 6. 部分送达与账本依赖

候选必须先整体校验与容量预留，再开始任何送达。验证所有气泡、op、引文、权限、注解及supersede目标；不能A已正式后才发现C协议非法。整个组一笔预算，不把气泡当免费扩容。

每个op推导所需的正式输入和候选气泡集合；仅全部依赖已送达时应用。即使仅引用历史/玩家消息，也建议最早在本组首条AI送达时应用，避免零回复的失败尝试留下模型推断。气泡提交、可用op、对应高光、inverse增量和未读序号必须同一会话事务成功后才能通知UI。

首版不引入通用依赖图：保留现有约束，supersede只能指向本次上下文提供、仍active的旧entry，同组不得重复触碰一个目标，也不得引用同组新建entry。这样禁止跨op写链，避免“前一op取消、后一op却生效”。若将来确需链式依赖，另设计拓扑与回滚，不能只检查来源ID。

inverse只包含实际应用操作；组撤回逆转已应用部分，取消未送达计划并释放剩余预留。来源涉及取消气泡的op/注解终止，不降级借其它引文强行入账。容量预留需覆盖总entry和任一前缀active峰值（不能拿后面的supersede给前面的add提前腾位置）；送达中影响账本的手工修改要串行或显式冲突，不能使候选悄悄改义。实现前用保存失败和容量边缘例子闭合。

## 7. 插话、CAS、多个玩家连发与停止

同会话接受输入、保存候选、送达和停止都经同一事务排序。每个玩家操作有client_action_id；送达键为group_id+气泡序号；重放同键返回原结果，payload不一致拒绝。网络丢响应先查权威结果，不重建重复消息。

建议普通插话即时保存为正式玩家事件，并加入待回应队列。连续短批按原顺序发完；组结束后原子认领当时所有未回应输入为下一请求的输入集合，保留各条ID、顺序及各自OOC，不拼成一句伪造单来源。一次请求回应这一集合，不每条连发都开请求。生成期间后到输入留给再下一组；不为每次输入自动取消已付费请求、无限重新生成。输入硬容量和总token预算沿现有门，未认领队列也需有界，不能无上限缓存。

当前base_revision==session.revision不足以支持这种并行：普通插话和未读游标更新会改变revision，却不必使旧短批失效。建议保留对外revision用于CAS，另设语义generation_epoch/组状态及input_cutoff_seq；普通追加输入不改变旧组所依据的历史前缀，停止、撤回、改语境等使epoch失效。提交必须验证对应epoch、组仍有效、输入前缀未撤改、账本目标及预留仍匹配；**不能简单删除当前revision检查**。需要按操作列出冲突矩阵和迟到结果测试后才实施。

停止按钮确定性取消当前生成或剩余待发，并递增失效标识；已经送达保留。停止不是删除玩家已保存输入，也不是自动恢复/自动再次调用；待回应输入显示可恢复状态，玩家下一次发送/显式继续才认领，避免点击停止后队列立刻重新生成。停止与B送达竞争以事务先后为准，成功返回停止后不得再送未提交气泡。

不能让LLM或关键词分类器持有硬停止权：字符串“别说了”可能是引用，普通字面匹配也会漏掉真实更正。角色应在下一语义回应尊重自然语言边界，但这不等于及时硬抢占已有队列。建议提供“停止并发送/立即打断”确定性动作，带OOC的发送也可设计为立即打断；具体入口由第10节选择。不能声称现有按钮或提示词已兑现此能力。

这暴露一个真实取舍：普通插话保持旧短批自然连续，会有旧内容来不及理解新边界的窗口。不能用模型“识别紧急程度”掩盖；需要明确硬控制入口、短且有界的批次，以及用户确认该产品语义。

## 8. 重试、撤回、归档、恢复与未读

| 情况 | 建议行为 |
| --- | --- |
| 请求失败且未保存有效候选 | 标记失败，保留输入；显式重试沿原协议/输入快照，不自动付费重试 |
| 候选保存后丢响应 | 读回原组，不再请求模型；同气泡幂等送达 |
| 保存某次送达失败 | 不广播成功、不增加未读、不应用半套op；恢复后重试该事务 |
| 撤回/重生成 | 仅最新且未被后续正式玩家输入依赖的组可操作；先终止旧余量，按实际inverse处理；历史中间组不任意替换 |
| 重生成失败 | 推荐旧已送达组保持正式，旧未送达不复活；新组成功保存并准备首送达时再原子替换旧组，明确显示“替换未完成” |
| 归档 | 保存旧正式前缀及对应审计信息；候选草稿与正式档案明确分区，任何召回/来源索引不读取归档替代分支 |
| 页面切换/关闭页面但本地服务仍运行 | 服务端继续已有送达，列表积累未读；客户端不担任唯一timer |
| 进程退出/休眠后重启 | 重建权威状态，已送达不重播；有效持久候选建议按恢复后的节奏继续，不伪造退出期间时间戳；旧停止/失效组不复活 |
| 崩溃时仍在模型请求中 | 标记interrupted，保留可重试输入，不自动再次付费；只恢复完整验证且已保存候选 |

重生成遇到在途玩家输入必须在同一锁内裁决：若新输入已正式保存，拒绝替换被依赖组，不偷偷迁移玩家回应到新剧情。多条被认领输入与组的关系保留，重试不重复创建玩家消息；撤回是否连同本组原输入撤回须保持既有操作含义，并在迁移门明确，不把新插话一并删掉。

未读建议采用每会话`last_read_ai_seq`：正式AI送达推进最新AI序号，客户端确认实际展示后单调ack；打开会话本身不是读完整历史。ack最多到已送达序号，不能覆盖之后的并发送达；后台不自动已读。恢复先读权威状态和游标，不把动画结束当已读证据。多个窗口按单调max合并，不引入跨设备云同步。

## 9. 旧协议迁移与分阶段出口

旧v1/v2正式双消息回合读取不猜分句，可投影为单气泡组且保留原ID/inverse。旧pending按现有协议身份恢复为interrupted/retry，不用新v3解析旧请求结果。上下文协议与输出协议分别版本化，不能因改存储就强制旧attempt换协议。

存储需要新明确版本、完整校验、原子单向迁移和可核对备份；未知较新版本只读拒写。先用合成旧会话证明正式来源、归档、inverse、pending/retry和OOC都无损，再允许写新数据。具体版本号、字段精确集合、容量计数和读写适配尚未冻结；本稿不授权仓促迁移真实会话。

实施顺序建议：

1. **C4-0 / P1行为基础，独立可做**：第1节短指导与装配/边界回归，仍single reply。它不是整个C4完成证据。
2. **C4-D / P1契约门**：回答第10节；补齐确切schema、预算、操作冲突矩阵、迁移及故障测试表。模型不能控制硬权限，语义等待不得变自动任务等不变量可现在冻结；持久写入仍等完整门。
3. **C4-A / P1领域基础**：严格解析组、来源映射、依赖计划、逐条事务、幂等、旧数据读取迁移；仅合成后端验证，不开放半成品UI。
4. **C4-B / P1交互闭环**：输入队列、CAS/epoch、停止、重试/批撤回/重生成、恢复和未读；用A/B/C+X/Y故障/竞争验证，未送达无假经历。
5. **C4-C / P1体验闭环**：前台分组/预览去重/正在输入、后台列表未读、确定性打断入口、已批准的节奏控制；宽窄屏及旧会话回归。
6. **C4-V / P1验收**：窄测后全量Python/Node/build/Edge、重启故障和宽窄截图；真实模型质量单列、付费调用另获授权。按仓库流程记录源码与当前证据，不沿用旧计数冒充通过。

不为了赶进度先落一个将被推翻的messages字段。若C4-0完成而第10节仍未决定，则停止C4多消息实现并报告设计门，不切去C5、容量扩展、心理学调用、跨会话画像、版本打包或远程操作。

## 10. 最多两个需要人的产品选择

1. **气泡节奏由谁掌握？** 模型具体定时、玩家固定速度，还是混合？推荐混合：模型决定内容分段与真实等待，程序确定有界送达，玩家调阅读速度。默认秒数/范围仍可在此选择之后由工程提出并校验，不把0.1秒历史下限当全部节奏已定。
2. **“连贯说完”与“马上停下”的入口怎样分？** 推荐普通发送先接收、短批后回应，同时提供确定性的“停止并发送/立即打断”；带场外纠正的发送可采用此硬打断路径。另一选择是任何发送都打断，响应新边界更快，但不再是用户描述的连续短批行为。自然语言仍需被角色尊重，却不能保证未经硬动作的文字在旧队列中即时生效；需要用户选择这一取舍，不能交给关键词/LLM分类代替批准。

其余工程参数由实现者在上述边界内负责，不把任务拆成反复询问用户每个M/C编号。当前真正独立可编码片只有C4-0；本稿完成意味着设计可讨论，不意味着整个C4产品和工程契约已冻结。
