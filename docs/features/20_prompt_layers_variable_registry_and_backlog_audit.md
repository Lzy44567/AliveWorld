# 提示词分层、变量注册表与 v1.5—v1.6 遗留审计

更新：2026-09-13  
状态：设计完成，尚未授权实施提示词重构

## 本轮边界

本轮只修复特殊气泡复制按钮和多行文本全屏编辑，并完成提示词架构审计。不得在没有等价性测试和迁移清单时直接删改正文提示词，也不得让新想法取代已确认的玩法主线。

## 当前代码事实

1. `core/prompt_studio.py` 目前登记 10 个切片，只有近期未来、正文结算、玩家行动权和连续性共 6 个切片可覆盖。
2. 状态栏并未丢失：`system_prompts.yml` 的 `settlement_prompt` 同时包含 `dynamic_bars`、`status_updates`、`npc_states`、Buff 和删除字段的说明及 JSON 结构。但它仍被包在 `story.settlement.core` 内，没有独立分区，因此开发者工作台无法单独查看、估算或覆盖状态栏协议。
3. 世界书捕获、工坊、暗流、记忆、偏好和生图提示词仍由各自模块拥有；注册表目前只显示其中两个“尚未迁移”的占位项，不是完整总入口。
4. “警察、保安、公序良俗”等文本同时出现在未来核心、正文核心和连续性切片中。它来自真实游玩缺陷修复，但重复且过于贴近单一案例。
5. 当前变量只使用 `world_info`、`character_info`、`style_info` 等少量字符串名；没有统一描述变量来源、类型、敏感性、空值语义和可用任务的注册表。

## 目标分层

提示词按职责分五层，分层不增加模型请求：

| 层 | 内容 | 可否被普通预设关闭 |
| --- | --- | --- |
| A. 引擎契约 | 输出结构、字段类型、玩家与系统权限、状态事务、后端依赖的不变量 | 否 |
| B. 玩法模块 | 状态栏、随机未来、暗流兑现、世界书捕获、快捷行动、偏好、记忆 | 对应玩法关闭时整片移除；必需校验仍由 Python 保留 |
| C. 体验预设 | 节奏、反套路、避免重复执法介入、描写倾向、俗称“预设/破限”的自定义内容 | 是，关闭后不得继续拼接 |
| D. 世界与角色资产 | 世界书、角色卡、实体、文风、已确认偏好和世界包建议 | 随载入状态决定 |
| E. 本回合数据 | 历史热窗口、记忆摘要、玩家行动、选中未来、待兑现影响、当前状态 | 每回合动态生成 |

玩家行动权的“不得替玩家做重大决定”属于 A 层权限契约；“不要反复引入警方”属于 C 层体验优化；“外部介入必须存在信息通道”属于 A/B 层通用连续性约束。这样可以删除案例重复而不撤掉真正的因果规则。

## 变量注册表

新增唯一 `PromptVariableRegistry`，提示词切片只能引用已登记变量。每个变量至少记录稳定 ID 与中文名称、值类型及渲染器、数据所有者和允许任务、空值语义、必需性、敏感级别、可用状态与 token 粗估；示例只用于编辑器帮助，不进入正式请求。

首批命名空间：

| 命名空间 | 示例 |
| --- | --- |
| `story.*` | `story.premise`、`story.history.hot`、`story.memory.summary`、`story.player_action` |
| `assets.*` | `assets.worldbook`、`assets.characters`、`assets.styles`、`assets.entities` |
| `player.*` | `player.character`、`player.preferences.confirmed` |
| `runtime.*` | `runtime.state`、`runtime.selected_future`、`runtime.causal_influences` |
| `rules.*` | `rules.output_schema`、`rules.story_length`、`rules.action_suggestions` |

编辑器后续提供可搜索变量表：显示名称、来源、类型、当前可用状态和用途，点击即可插入占位符；未知变量、必需变量缺失和跨任务越权都在保存前阻止。

## 状态栏拆分

状态栏继续与正文共用一次结算请求，但拆为三个可观察切片：

1. `story.state.contract`：字段 schema、事务和 Python 校验依赖，不可由内容预设关闭；
2. `story.state.guidance`：何时新增、更新、删除状态条，开发者可版本化覆盖；
3. `story.state.world_defaults`：世界包或内容预设提供的初始展示建议，可关闭。

状态栏结果仍由 `state_manager.py` 验证和提交。提示词编辑不能绕过字段校验，也不能直接写存档。

## 迁移顺序与验收

1. 先建立变量注册表、任务/槽位枚举和旧组装结果快照，不改变输出文本。
2. 从 `settlement_prompt` 抽出状态栏契约、正文叙事职责和世界变化短信号；从未来核心移除与连续性切片的重复文本。
3. 将案例型体验修复改写成题材无关规则，并把可选的反套路倾向放入内建体验预设。
4. 迁移世界书捕获，再依次登记暗流、记忆、偏好、工坊和生图；每次只迁移一个任务族。
5. 最后实现内容预设/模型适配预设的选择、导入导出和关闭即零拼接。

每一步必须验证：组装顺序稳定；必需变量不遗漏；关闭功能后相关切片 token 为零；状态栏 JSON、玩家行动权和世界变化评测通过；模型调用次数不增加；日志 manifest 能解释每段文本来源。

## 下一主线判断

本轮 UI 修复完成后，下一开发重点不是给角色卡、实体或文风再增加孤立功能，而是：

1. **提示词架构第二阶段（前置）**：变量注册表、状态栏独立切片、底层契约与体验预设分层；
2. **世界书玩法主线（P0）**：题材无关的世界变化短信号与按需详细捕获；
3. **回合重演与分支（P1）**：待世界状态/修订边界稳定后实现，避免分支复制不一致状态；
4. 角色提取、深层偏好、云生图与移动端保持后置。

因此，对“游戏模式、角色卡、世界书、实体库、文风、提示词”的直接回答是：**先完成提示词基础设施，再回到世界书通用捕获；其余资产域不是下一轮主线。**
