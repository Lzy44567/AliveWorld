# AliveWorld 迭代开发循环

本文件把长期开发中反复确认的协作规则固化为可执行循环。它减少重复沟通，但不替代涉及玩法、隐私、商业路线或不可逆数据迁移的用户决策。

## 1. 证据基准

1. 读取总纲、对应功能文档、原始手稿和决策池；原始手稿优先。
2. 检查分支、提交、工作树、版本号和最近更新日志。
3. 阅读当前实现、测试、日志和真实数据结构，不根据旧对话直接套代码。
4. 工作树出现来源不明的改动时停止；玩家数据和密钥永不纳入提交。

## 2. 需求路由

每条新想法先归入一种类型：

- 缺陷：实际表现偏离既有契约，按风险决定当前修复。
- 体验问题：会误操作、阻断核心流程或反馈不可见时立即修；纯视觉精修集中处理。
- 功能扩展：写入对应功能文档，明确 P0～P3，不因临时灵感自动开发。
- 架构/商业/隐私决策：列出代价和可逆性，达到设计门后再编码。

### 主线与任务切换纪律

每轮开始时必须从仓库文档恢复并明确唯一活动主线：最终目标、当前阶段目标、已经完成的证据和下一可验收切片。新出现的灵感、体验问题或缺陷先记录和分级，不自动替换主线。

只有以下情况可以插队：数据丢失、隐私或安全风险、构建/运行阻断、基础契约或架构损坏，或用户明确要求立即切换。切换前必须说明原任务完成到哪里、切换原因、临时还是永久改线，以及返回条件。插队完成后默认回到原主线。

“先讨论”“先设计”“先记录”“暂时不开发”都不是实现授权。局部功能达到 MVP 契约且没有 P0/P1 缺陷后，不继续无限严格化或视觉抛光，应推进版本主线。

## 3. 设计门

大功能开发前至少明确：玩家目标、非目标、数据所有者、生命周期、权限/隐私、失败恢复、模型与 Python 责任边界、UI 最短路径、兼容迁移和验收方法。仍有会改变数据模型或玩家体验的关键分歧时先讨论；实现细节可由 Codex自主选择。

## 4. 可回退切片

每轮只选择一个可独立验收的结果，并在动手前列出文件和职责：

- 领域逻辑进入责任单一的后端模块。
- API 只做校验、调用和响应映射。
- 前端 API、状态和界面组件分离。
- 主文件只统筹，不堆放完整功能。
- 提示词工程与代码工程分别记录和测试。

## 5. 契约优先实现

先定义输入、输出、状态转换、错误类别和持久化边界，再写实现。LLM 返回必须经过结构化解析、校验、有限重试和安全回退；能由 Python 确定的计时、ID、概率、生命周期和文件操作不交给模型猜测。

## 6. 四层验证

1. Python 领域/API 回归：精确验证状态、文件和协议。
2. 隔离假 LLM/ComfyUI：验证提示词拼接、任务路由、错误和异步恢复，不消耗真实额度。
3. Playwright 玩家端：操作真实界面并检查 DOM、网络、磁盘和刷新恢复；可视化模式只负责展示步骤及截图抽查。
4. 人工质量验收：真实模型文学质量、生图质量、世界观合理性、长篇体验和干净 Windows 便携包。

任何失败都先区分代码缺陷、环境问题、供应商问题和内容质量问题。

## 7. 版本与溯源

每轮完成后依次执行：

1. 更新对应设计实现状态和 `docs/CHANGELOG.md`。
2. 运行语法检查、Python 回归、前端构建和风险相称的浏览器场景。
3. `git diff --check`，确认没有数据、密钥、构建产物和无关改动。
4. 使用版本节点与 `codex-gpt5.6sol` 作者标签提交到开发分支。
5. 只有发行候选通过人工门禁后才打 tag、构建 ZIP、写 Release 简介并发布；Release 简介以仓库内版本说明为唯一来源。

## 8. 反馈闭环

问题记录必须包含版本、操作步骤、期望/实际、日志 trace 和是否可复现。定位到引入提交后，选择前向修复或回退；修复场景要转成自动回归。新灵感进入决策池，不与当前缺陷混在同一提交。

## 9. Skill 与项目接手协议

2026-09-12 已建立通用 `long-running-software-development` Skill，负责跨项目的主线保护、设计门、可回退切片、验证与证据交接。AliveWorld 的实时项目事实不复制进 Skill，而由仓库根目录 `AGENTS.md` 指向唯一活动目标、总纲、功能文档、路线图、决策池、更新日志和测试指南。

这种分工避免一份巨型提示词同时混合通用方法和易过时的项目状态：

- Skill 只保存可迁移、低变动的方法。
- `AGENTS.md` 只保存稳定的启动阅读顺序和权限边界。
- `ACTIVE_DEVELOPMENT_GOAL.md` 保存唯一主线、当前切片、验收与进度，随开发更新。
- Git、代码和测试是“是否已经实现”的最终证据。

未来只有在出现多次、稳定且确实属于 AI 游戏而非普通软件的重复开发模式后，才抽取独立 `ai-game-development` Skill；不提前固化未经验证的流程。Skill 和接手协议都不能代替审美、玩法、商业方向或不可逆数据决策的用户选择。
