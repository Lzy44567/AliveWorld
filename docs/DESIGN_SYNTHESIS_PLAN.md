# 完整游戏设计案：收口计划

更新：2026-10-12。当前阶段仅产品设计。241项总索引及24–29讨论稿是来源，不把所有候选自动升级为用户确认。

## 已明确的共同方向

故事是主特色，角色模式独立，工坊协作创作；世界事实、玩家控制、局内副本与可追溯变化保持一致。可选数值、模板开局、卡片积累、偏好参与、世界包创作、角色提取为已确认方向；具体默认与UI方案仍分项标记。

## 可自主推进的设计交付

1. 合并现有讨论，形成简明的当前决定表，标明已确认/建议/后置；旧轮问题用链接保留历史，不让后续AI逐轮猜最终结论。
2. 完整故事流程：从选择内容/开局到行动、判定、正文状态、后台整理、持续记忆、撤回/分支；标出用户动作、模型职责、额外调用和等待位置。
3. 人物生命周期：初次出现、稳定身份/别名、记忆、当前在场、实体升格/休眠、角色卡提取及跨世界使用；不同状态不混同为一个删除按钮。
4. 创作流程：文稿/卡片导入、世界包项目、规则和剧情节点、融合与逐项/批量审阅、试玩与本地发布。功能未实现处明确标注。
5. 提示词职责表：引擎契约、未来、正文、暗流、整理、工坊分别读什么/产出什么；静态前缀、动态取材、可选切片和预设边界。不预写长篇生产提示词冒充验证完成。
6. UI与设置：先新建、故事主界面、工坊三个任务原型；同一任务简单默认、高级折叠；待用户看具体原型后决定视觉取舍。
7. 将上述收口为游戏详细设计案，给设计完整度/实现状态/验证状态、模块依赖、有限首版范围和后续升级顺序。完成设计不自动授权编码。

## 需要用户参与的决定

只对会改变产品体验或世界规则的取舍提问：关键界面原型、首个正式版范围、未有明确答案的跨模式权限/固定剧情冲突。一次集中少量问题，提供推荐及具体游玩例；实现结构、字段名、可逆布局细节自行提出。

不再询问已明确需求是否需要。默认候选可以先设计成可审阅方案，但不能写成“用户已确认”；没有答复不视为批准。付费模型质量评估、编码、打包或发布不因设计推进自动启动。

## 当前后置

故事内私聊用途尚未明确，保留为交互体验假设；先通过角色身份/头像/直接互动原型观察是否有必要。群聊完整引擎、任意代码小游戏、通用插件、社区后台等不阻塞主游戏设计。

## 收口标准

每个核心模块能回答玩家如何开始、输入什么、看到什么、内容如何持续生效、出错如何纠正、是否多花调用，并有少量完整案例。远期模块明确目的/边界/依赖即可，不要求无限提前细化。

产物应供用户一次审阅模块方案、供实现者连续开发；不通过增加阶段缩写、开关或校验框架来掩盖未解决的产品问题。
